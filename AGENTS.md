# Repository Guidelines

## Project Structure & Module Organization

`aardvark/` contains the Python source for the weather model. Core model code lives in `models.py`, `architectures.py`, `set_convs.py`, `vit.py`, and `unet_wrap_padding.py`; training and finetuning entry points live in `train_module.py`, `trainer.py`, `finetune.py`, and `e2e_train.py`; data loading utilities live in `loader.py`, `loader_utils_new.py`, and `data_shapes.py`.

`training/` contains shell scripts for staged encoder, processor, decoder, and end-to-end training. These scripts document the research pipeline but depend on local data and compute infrastructure. `scripts/` contains data preparation, validation, plotting, and download helpers. `notebooks/` contains runnable demos for sample data and forecasts. `data/` stores small sample artifacts, grid coordinates, and normalization factors; keep large datasets, memmaps, NetCDFs, and checkpoints external.

## Build, Test, and Development Commands

- `conda env create -f environment.yml`: create the Python 3.8 CUDA/PyTorch environment.
- `conda activate aardvark-env`: activate the development environment.
- `jupyter lab notebooks/forecast_demo.ipynb`: run the forecast demo with sample data.
- `bash training/train_encoder.sh`: illustrative encoder training command; requires unavailable local pipelines.
- `python scripts/check_obs_memmaps.py ...`: run targeted data validation helpers when adding or changing preprocessing outputs.

There is no package build step or formal test runner configured in this public snapshot.

## Coding Style & Naming Conventions

Use Python with 4-space indentation and follow the surrounding PyTorch style: explicit tensor shapes, descriptive variable names, and small helper functions for repeated shape/channel logic. Prefer `snake_case` for functions, variables, script names, and CLI arguments. Keep model classes in `PascalCase`, for example `ConvCNPWeather` and `Processor`.

`black==24.4.2` is included in the environment. Format changed Python files with `black aardvark scripts` before submitting broader edits.

## Testing Guidelines

No dedicated `tests/` directory exists. Validate changes with the narrowest runnable artifact: notebooks for inference behavior, `scripts/check_*` utilities for data products, and small Python smoke tests for model construction or tensor-shape changes. When changing channel counts, time frequency handling, or losses, test both the expected shape calculation and the downstream module that consumes it.

For this Windows workstation, reuse the isolated CPU test environment described in
`docs/windows_test_environment.md`. It records the interpreter path, dependencies,
regression command, Windows sandbox limitations, and validation scope. Check that
the temporary environment still exists before using it; do not change the global
Python or original Conda environment to run these tests.

## Commit & Pull Request Guidelines

Recent history uses short imperative messages, often Conventional Commit prefixes such as `fix:` and `chore:`. Prefer messages like `fix: handle daily ERA5 channel counts` or `chore: ignore generated bytecode`.

Pull requests should include a concise summary, the affected pipeline stage, commands or notebooks used for validation, and any external data or checkpoint assumptions. Include plots or screenshots when changing notebook outputs or visualization scripts. Do not commit generated caches, large datasets, model checkpoints, or local run logs.

## Agent-Specific Instructions

Treat training scripts as documentation unless the user provides the required local data paths. Preserve sample data and normalization files, and avoid rewriting notebooks unless the requested change specifically affects demo behavior.

For SDPA, FlashAttention, or multiscale ViT follow-up work, read
`docs/vit_optimization_review_memory.md` for the 2026-11-01 proposal review,
repository findings, validation requirements, and recommended experiment sequence.
