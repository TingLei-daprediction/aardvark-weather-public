4u_sfc workflow (30 channels = 24 upper-air + 6 surface)
- Generate truth memmaps (pressure-level + surface): `sbatch run_prep_era5_truth.sh`
- Compute norms from memmaps:
  `python scripts/compute_era5_norms.py --data_dir <data_root> --output_dir <data_root> --era5_mode 4u_sfc --res 1 --years 2007 2008 ... 2019 --grid_dir <repo>/data/grid_lon_lat --time_freq 1D`
- (Optional) Build climatology for 4u_sfc:
  `python scripts/build_climatology.py --data_dir <data_root> --era5_mode 4u_sfc --res 1 --years 2007 2008 ... 2019`
- Train with `--era5_mode 4u_sfc --out_channels 30`
- Processor (forecast) input channels: loader builds y_context as concat(y_context_obs + elev(4) + aux_time(5)).
  For 4u_sfc, strict derivation would be 30 + 4 + 5 = 39 channels.
  The original 4u processor script uses 35 (24+11), so 4u_sfc script mirrors that as 41 (30+11).
  This is a known uncertainty; consider asserting against loader-derived channels for forecast mode.
- Decoder (downscaling) uses AardvarkICDataset/ForecastLoader context with era5_mode-specific norms.
  4u_sfc adds 30-channel context; new scripts train_decoder_4u_sfc.sh set in_channels 42 (legacy +12 pattern).
  This is another uncertainty; verify expected channels from y_context composition before final runs.
- End-to-end: added training scripts for 4u_sfc without changing default 4u behavior.

Processor/decoder setup uncertainty summary (for external review)
- Processor (forecast) input y_context is built as concat(ERA5/IC fields + elev(4) + aux_time(5)).
  Strict derivation gives 24+9=33 channels for 4u and 30+9=39 for 4u_sfc.
  Legacy scripts use in_channels=35 for 4u, implying +11; mirrored to 41 for 4u_sfc.
  Unclear if paper includes extra channels (e.g., climatology, masks, or legacy conventions).
- Decoder (downscaling) input channels: legacy script uses in_channels=36 for 4u (implies +12).
  Mirrored to 42 for 4u_sfc. Also unclear vs strict +9 derivation.
- Need to verify paper’s exact processor/decoder input composition and channel counts.
- Bug note: `models.py` used `torch.ones_like(elev[:, :5, ...])` to size aux_time grids.
  `elev` has 4 channels (orog, lsm, sin(lat), cos(lat)), so this mismatched aux_time (5 features).
  Fix: size the aux_time grid using `aux_time_current.shape[1]` instead of `elev` channels.
- cltorg bug? note: `aardvark/models.py` had `elev = torch.flip(task["era5_elev_current"].permute(0, 1, 3, 2), dims=[2])`;
  temporarily commented to test encoder shape alignment.
- cltorg bug? note: `aardvark/vit.py` per_var_embedding=False path was inconsistent:
  MLP outputs 256 channels but PatchEmbed expected `in_channels` (e.g., 277).
  Fixed by setting PatchEmbed in_channels to 256 and leaving commented original lines.
- ERA5 NaN note: pressure-level ERA5 fields can contain NaNs at some grid points (not whole timesteps),
  which poisoned mean/std in `mean_4u_sfc_1.npy`/`std_4u_sfc_1.npy` when using plain sums.
  Best practice: use NaN-aware stats (`np.nansum` + per-channel valid counts) and optionally
  fill NaN/Inf in memmaps via `--fill_nan 0.0` in `scripts/prep_era5_truth.py` before training.

RTMA-OK computational efficiency (2026-07-22)
Retrieval keywords: computational efficiency, RTMA performance, H100 utilization,
training throughput, convergence efficiency, DDP scaling, ViT token cost.

- Workload: January 2022 hourly RTMA-OK surface encoder, about 719 samples; 2 H100 GPUs,
  DDP, batch_size=1 per rank, 300 epochs per run. A chained weights-only warm start has
  produced about 600 epochs in roughly two days.
- Correct step count: DistributedSampler pads/splits about 720 samples across two ranks,
  so batch_size=1 gives about 360 synchronized optimizer steps per epoch, global batch=2.
- The current vit_assimilation encoder uses constant-rate Adam. The hard-coded cosine
  scheduler in trainer.py is used only when decoder == "vit", so it is NOT active here.
- Current warm start restores model weights only. It resets Adam moments, epoch numbering,
  scheduler state (if one is later added), and best-loss history; it is not a true resume.
- Full validation runs every epoch. The encoder path does not save every forecast every
  epoch, but it performs CPU transfers, unnormalization, physical-space loss work, and a
  complete validation forward pass. Validate every 5 epochs and compute/save expensive
  physical diagnostics only on improvement or at a wider interval.
- Do not add DataLoader workers blindly. Dataset __getitem__ currently moves tensors to
  CUDA. Proper prefetching requires returning CPU tensors, moving batches to the rank GPU
  in the trainer, then enabling pin_memory, non_blocking transfers, persistent_workers,
  and a small tested num_workers value.
- Benchmark one GPU with batch=2 against two GPUs with batch=1. Both have global batch=2;
  one GPU may win by avoiding an all-reduce every small step. Then test per-rank batch 2
  and 4 subject to memory. Larger batches reduce optimizer updates per epoch, so compare
  by samples/updates and convergence, not equal epoch count alone.
- H100 BF16 can accelerate the ViT, but keep ConvDeepSet coordinate/distance calculations
  in FP32. Normalized lon/lat differences are small and may lose precision under BF16.
- RTMA-only model construction could omit unused global-observation modules and may allow
  DDP find_unused_parameters=False, avoiding graph traversal and unused-parameter work.
- ConvDeepSet opportunities: cache static station-to-grid squared distances, recompute only
  Gaussian weights as learned length scales change, and vectorize variables when station
  coordinates are shared.
- Likely architectural hotspot: Grid B is 384x192 with patch_size=3, producing 128x64 =
  8192 global-attention tokens. Attention cost grows quadratically with token count. Profile
  before assuming I/O is dominant. Longer-term options include SDPA/Flash Attention,
  windowed or hierarchical attention, a smaller inner grid, larger patches, or reduced
  width/depth, with fine-scale analysis quality checked explicitly.
- Convergence improvements: true optimizer/checkpoint resume, short LR warmup, cosine decay
  based on the actual total optimizer-step count, final LR near 1e-6, gradient clipping,
  validation all-reduce across ranks, and early stopping.
- Recommended order: (1) time data/forward/backward/validation and inspect GPU utilization;
  (2) benchmark 1-GPU batch=2 vs 2-GPU batch=1; (3) reduce validation frequency and expensive
  diagnostics; (4) test per-rank batch 2/4; (5) selectively apply BF16 to ViT; (6) implement
  true resume and an appropriate LR schedule; (7) optimize the measured SetConv or ViT
  bottleneck rather than relying on unprofiled assumptions.
